# BRDSC

[English](README.md) | 简体中文

**BRDSC** 是一套工程判断框架，用于让代码与设计在系统层面保持协调一致。

* **B — Boundary（边界）**
* **R — Responsibility（职责）**
* **D — Dependency（依赖）**
* **S — Single Authority（单一权威来源）**
* **C — Consistency（一致性）**

它面向工程师和能够理解代码仓库的 AI 编程智能体，帮助做出设计、评审和重构决策。它不要求采用 DDD、整洁架构、事件、仓储或其他特定架构风格。

## 为什么需要 BRDSC？

代码可以正常运行，却越来越难以修改：相似的规则散落在不同位置，职责在各层之间游移，每个新功能又引入一种解决相同问题的方式。

BRDSC 帮助判断什么样的结构适合当前系统及其需求，同时检查拟引入的抽象是否带来了足以抵偿复杂度的价值。

核心问题是：

> 这个改动是否让系统整体更加协调一致？有什么证据支持这个结论？

## 五个判断维度

| 维度 | 需要明确的问题 |
| --- | --- |
| 边界 | 哪些概念需要独立的归属、生命周期或一致性边界？ |
| 职责 | 谁负责每种行为？下一个相似的改动应该放在哪里？ |
| 依赖 | 哪些依赖关系是有意设计的？哪些暴露了内部细节，或迫使无关部分一起修改？ |
| 单一权威来源 | 谁定义每条业务规则？如何在不同入口和并发执行时保证规则成立？ |
| 一致性 | 相似代码如何解决这个问题？是否有具体理由采用不同方式？ |

这些维度用于辅助推理。不要为它们打分，也不要求每次评审都讨论全部五个维度。

实践中需要注意两点：

* 协调多个业务能力可以是应用服务的合理职责。仅凭出现不同的业务名词或多次调用，不足以证明应该拆分工作流。
* 业务规则的语义归属与原子执行保障，可以分别体现在业务能力和数据库操作中。条件更新和数据库约束可能是保证规则成立的关键机制。单一权威来源不要求把 SQL 检查搬进实体方法，也不要求删除防御性校验。

## 使用 Skill

[SKILL.md](SKILL.md) 是智能体使用本框架的入口。元数据说明 BRDSC 的适用场景，正文包含核心原则、调查流程和输出要求。

当任务涉及模块边界、职责归属、依赖关系、共享业务规则，或需要权衡是否引入抽象时，可以使用 BRDSC。格式调整和机械性修改不需要进行 BRDSC 评审。

将 Skill 安装到所用智能体支持的位置后，可以这样提问：

```text
使用 $brdsc 评审这个 PR 的事务边界和业务规则归属。

使用 $brdsc，参考现有退款和取消流程，判断退款资格校验应该放在哪里。

使用 $brdsc 指导这次改动的实现，保持项目现有的依赖关系和持久化约定。
```

评审请求产出问题和建议；实现请求则在所要求的改动范围内应用这套框架。两者都不意味着要对整个仓库进行架构改造。

## 如何做出判断

1. 明确行为、业务不变量、副作用和相关需求。
2. 检查发生改动的能力、它的调用方与被调用方，以及相似实现。
3. 区分已观察到的事实、推导出的后果，以及会影响判断的未知条件。
4. 找到实际推动设计变化的因素，选择能保持系统协调一致的最小改动。
5. 验证相关影响，并说明实际完成了哪些检查。

建议应指向具体代码或已提供的需求，并解释问题的触发条件、后果和影响范围。关于生命周期、重试行为或未来需求的无依据断言，不能作为证据。

“无需改动”是有效结论。信息不完整时，应说明判断的局限，并明确建议成立的条件。保留当前结构，并不能证明其行为一定正确。

现有惯例有价值，但有证据支持的正确性或数据完整性问题，可以成为打破惯例的理由。应说明替代原则和受影响的执行路径；需要迁移时，应明确新旧方式暂时共存的安排。

## 判断案例

[判断案例（英文）](references/cases.md) 包含以下明确给出需求前提的模拟场景：

* [工作流协调](references/cases.md#workflow-coordination-can-remain-together)：对必须一起提交的业务能力，保留统一的协调者。
* [数据库约束保障](references/cases.md#a-repository-operation-can-own-a-transition)：在共享仓储操作中保留带条件的状态转换。
* [改变有害惯例](references/cases.md#correctness-can-require-breaking-a-convention)：即使附近代码使用相同的不安全模式，也应修复并发竞争问题。
* [证据不足](references/cases.md#side-effects-require-evidence-about-failure-semantics)：区分语义尚不明确的调用顺序，与已有证据支持的投递和重试问题。

这些案例展示了不同证据如何导向不同建议，其中的前提不能直接套用到正在评审的代码上。

## 验证 Skill 的改动

修改后应检查元数据和引用链接。如果改动涉及判断流程，还应使用贴近实际的请求进行验证，并提供足够的原始代码和需求，以便判断回答是否合理。

适合验证的场景包括：无需重构的合理设计、有害的现有惯例、由数据库保障的业务不变量，以及上下文不足的代码片段。检查建议是否遵循已提供的证据、保持任务范围，并区分建议执行的检查与已经完成的测试。

仅通过格式校验，不能证明 Skill 能做出可靠的工程判断。
